=== TASK 1: Split ExcelWriter into write-only + table helpers ===

integrations/excel_writer.py currently mixes writing logic with lookup/
structural helpers that aren't about writing: _find_row, _find_tag_id,
_next_row, _next_tag_id, _link_exists, _expand_table. These search for
rows, compute indices, and check existence — none of them write a cell.

Move them into a new module (e.g. integrations/excel_table_helpers.py),
either as free functions or a small helper class, whichever better matches
the style already used for excel_workbook.py's open_workbook and
create_column_map (which already went through the same "extract shared
logic" treatment). ExcelWriter should end up containing only the save_*
public methods and the _write_*_row private methods that actually place
values into cells. Update every caller (ExcelWriter itself, and
ExcelReader if it uses any of these) to import from the new location.

=== TASK 2: Rename Portuguese identifiers to English ===

Many variable, method, function, and parameter names across the codebase
are in Portuguese and should become English, EXCEPT for anything that is
a literal external identifier — renaming those would break the program
at runtime. Do NOT rename:
- SQLAlchemy ORM model class names or their column attributes (Funcionarios,
  Tarefas, DetalhesTarefa, Horas, Etiquetas, TarefaEtiqueta, and fields like
  canonical_name, jira_email, responsavel_id, etc.) — these map to real
  Postgres tables/columns and are documented as staying in Portuguese
  deliberately.
- Any literal string referencing an Excel sheet name, table name, or column
  header (e.g. "BASE_TAREFAS", "dim_funcionario", "responsavel", "titulo",
  the keys used in TASK_COLUMN_MAP, or dict keys read from DIM_FUNCIONARIO
  headers in ExcelReader) — excel_writer.py's own module docstring already
  explains why these can't be translated.
- Environment variable names in Settings.

DO rename: local variables, private helper method names, function
parameter names, and class/method names that are pure Python-side naming
with no tie to an external system. Concrete examples already known to need
this: PostgresClient.upsert_funcionario → upsert_employee (keep the
parameter names matching what they represent, e.g. canonical_name stays
since it mirrors the DB column), upsert_tarefa → upsert_task, upsert_hora
→ upsert_time_entry, upsert_etiqueta_e_vinculo → upsert_tag_and_link;
EmployeeSyncService's internal variables (linha → row, linhas → rows,
unicas → unique_rows, duplicadas → duplicate_rows, chave → key,
jira_vistos/clockify_vistos → seen_jira_emails/seen_clockify_emails);
nome_para_id in pipeline.py → name_to_id or similar.

Search the whole repo systematically for this pattern rather than relying
on the examples above — there may be more instances in files not
mentioned here. When in doubt about whether an identifier is tied to an
external system, leave it in Portuguese and flag it in your summary at the
end rather than guessing.
